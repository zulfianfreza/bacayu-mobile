# Taste
- All user-facing strings must go through `context.l10n.xxx` (ARB-based `AppLocalizations`); never hardcode UI strings like labels, buttons, or error messages. Repeatedly and explicitly stated ("Semua label lewat context.l10n"). Confidence: 0.95
- Follows feature-first Clean Architecture: each feature is split into `domain/` (entities, repositories, usecases), `data/` (models, datasources, repository impl), `presentation/` (cubits, pages, widgets). Confidence: 0.85
- Handles errors functionally with `Either<Failure, T>` (dartz) and a sealed `Failure` type; exceptions are mapped to `Failure` at a single point and never allowed to escape to the UI. Confidence: 0.85
- Keeps layer boundaries strict via interfaces (e.g. `core/network` must not import from `features/*`; presentation talks to core through abstractions). Confidence: 0.7
- Strongly prefers reusing existing widgets and usecases across features over duplicating logic (cross-feature composition is acceptable and encouraged). Confidence: 0.75
- Prefers optimistic UI updates with rollback on failure for toggles (e.g. like/follow buttons) rather than waiting on the network. Confidence: 0.65
- After a mutation, updates local state (replace the single affected item) rather than refetching the whole list. Confidence: 0.6
- Treats the project's `CLAUDE.md` as the source of truth and expects prompts/implementation to conform to it. Confidence: 0.7
- Expects every feature to ship with tests (unit tests for cubits/usecases, widget tests for widgets) and requires `flutter analyze` clean and `flutter test` all passing before work is considered done. Confidence: 0.85
- Uses `go_router` (including `StatefulShellRoute`) for navigation and `get_it` + `injectable` for dependency injection. Confidence: 0.65
- When the backend contract is missing something a mobile feature genuinely needs, stops and asks rather than assuming or fabricating data. Confidence: 0.7
- Writes and works in Indonesian (Bahasa Indonesia) and expects Indonesian-language responses. Confidence: 0.65
- Dislikes ellipsized/truncated user-facing text (repeatedly raised for book titles on a share card and in `SessionActivityCard`): expects the full string to be shown, either by letting the container grow or by adapting the type (auto-fit/shrink) rather than clipping with `maxLines` + `TextOverflow.ellipsis`. Confidence: 0.8
- Pragmatic about implementation approach when reporting UI defects: reports the symptom (e.g. a layout overflow) and explicitly leaves the fix up to the agent, allowing either adapting the existing widget or introducing a distinct variant ("disesuaikan atau mau dibedakan juga tidak masalah"). Confidence: 0.55
- Expects the agent to leave their running dev session untouched: when a device/simulator already has the app running, do NOT stop or restart it — work around it and verify changes another way (tests, separate renders). Explicitly requested ("untuk device yg running bisakah tidak perlu di stop"). Confidence: 0.8
- Prefers UI icons/artwork wired through a single swappable replacement point, and is happy to use existing/placeholder assets (built-in Material icons, asset paths) for now rather than sourcing final artwork up front — they intend to swap the artwork themselves later without code changes ("siapkan untuk mengambil dari asset image, nanti saya ubah sendiri"; "pake yg ada dulu nanti saya ubah"). Confidence: 0.7
- When redesigning form/auth pages, wants each input to carry its own visible label, an icon on the right side of the field, and the form block centred on screen. Confidence: 0.5
- Prefers minimal active-state styling: indicate the selected/active nav item through icon and text colour alone, without a background pill or fill. Confidence: 0.55
- Scopes change requests tightly and calls out what must stay unchanged: explicitly names adjacent sections/screens to leave alone ("buat as is saja") and expects only the requested widget/page to be redesigned, not a broader refactor. Confidence: 0.6
- For book/library lists, prefers a cover-first card layout — grid of 2 columns with the cover on top and metadata (title, author, progress/status) underneath. Confidence: 0.5
- Welcomes the agent's own suggestions over literal execution — when supplying a draft (e.g. copy text) they explicitly invite a better alternative if one exists ("atau lainnya jika ada rekomendasi"). Confidence: 0.55
- Treats activity/feed UI as social: items should make authorship explicit by showing the posting user (avatar + name) above the content, not just the book/badge itself. Confidence: 0.5
- Frames requests in terms of future product direction/relocation of features (e.g. "activity will later move to the profile page") and expects the current implementation to be structured so that later move is cheap. Confidence: 0.45
- For the home-page weekly activity strip, prefers a redesigned "days of the week" row: a circle per day with the day label underneath, and a green check mark on days where reading happened (explicitly requested "bulat dan inisial hari dibawahnya, kemudian berikan centang hijau pada hari yg active"). Confidence: 0.5
- Centralises colours in the theme layer (`lib/core/theme/app_colors.dart`) and extends it by editing the palette definitions there — adding a named scale (e.g. a "slate" palette) or filling in the missing steps of an existing one (e.g. "lengkapi warna tangerine") — rather than hardcoding colours inline at the widget. Confidence: 0.6
- Wants colour ramps to be complete ladders, not just a handful of anchor values: expects the full 50–900 scale to exist for every family (asked to complete tangerine's missing 200/400/600/800, then asked to complete the remaining brand ramps the same way), so components have fine-grained tint/shade steps. Confidence: 0.7
- Wants semantic state colours as first-class palette tokens (`success`, `warning`, `danger`, `info`) mapped onto real colour families, so a state is never an ad-hoc one-off hue. Confidence: 0.6
- Uses Tailwind's palette as the reference when the theme needs hues the brand does not own ("Seperti pada tailwind", naming purple/violet and others at full 50–900), while keeping the app's own brand families distinct rather than duplicating them (e.g. no separate orange when tangerine already serves). Confidence: 0.6
- Pragmatic about running the full test suite during iteration: prefers to defer the whole `flutter test` run to the end of the work (or when explicitly asked), rather than blocking every change on it, and is fine with only focused tests in the meantime ("flutter test bisa di skip aja dulu, bisa di akhir"). - Directs visual redesigns by naming a well-known consumer app as the reference (e.g. "seperti card pada duolingo") and expects the agent to distil that app's signature traits and express them through the project's own theme tokens, rather than copying it literally. "Duolingo style" is their standing shorthand for the app's target look, applied page by page as a whole-page treatment ("coba implement duolingo style pada halaman ..."), and invoked generically with "juga" ("redesign halaman <@path> dengan style duolingo juga") to mean the same look extended to yet another page. Confidence: 0.7
- Works through a redesign incrementally — component-by-component on a page ("coba bagian RangeSegmentedControl nya, masih di page yg sama"; "coba bagian heatmap nya") and then page-by-page once a page is done ("coba sekarang login page dan register page"; "coba sekarang untuk halaman shelf"; "coba home page"; "coba sekarang redesign halaman @lib/features/stats/presentation/pages/stats_page.dart") — always by naming the next page/component target with a terse one-liner, any of "coba sekarang ...", "coba <bagian> ...", just "coba <page>", or a question form like "kalo <@path> bagaimana yaa", optionally with an @-path to the file, and expects it rebuilt in the same visual language as the parts already redesigned, so the page/app reads as one system rather than mixed styles. Confidence: 0.75
- Treats sibling screens in the same flow as one surface: login and register must share measure, centring, and the same field/button widgets, so navigating between them shifts nothing and neither is styled independently. Confidence: 0.55
- Prefers consolidating closely related content into one container rather than leaving it as separate stacked cards/sections (e.g. asked to merge the streak number and the weekly heatmap strip into a single card). Confidence: 0.5
- Likes cards drawn with an actual border — thin on top and sides, with a slightly thicker bottom edge that reads as the card's base — as an alternative to a raised slab/shadow. Prefers that border in the cool slate neutral (`slate200`) rather than the app's warm `line` hairline, which reads muddy/dirty against a white card body ("untuk beberapa border bisakah menggunakan slate saja?"); a card whose surface is itself tinted should instead carry a border drawn from its own colour ramp (e.g. `sunshine300` on the yellow badge card). Treats the slate rule as app-wide chrome and happily extends it to every hairline that sits on white — when offered, approved moving input borders (`inputDecorationTheme` + text field), in-card dividers and the theme's `Card` border onto `slate200` too, leaving `line` only for surfaces that are meant to be warm (chip/pill backgrounds) and the nav chrome border. Keeps asking for it on more surfaces and refers back to it by name ("implement border card duolingo juga pada activity card dan shelf book card compact"). Confidence: 0.7
- Prefers widgets/layout slots sized by their own content rather than a hardcoded fixed height: asked for the compact shelf card to "fit the content", then kept applying the same rule to further surfaces (continue-reading carousel, activity-session card), expecting intrinsic sizing (e.g. `IntrinsicHeight`) and stacked facts compressed so a short item stays short instead of being padded out to a fixed slot. Confidence: 0.7

Confidence: 0.7

Confidence: 0.55
